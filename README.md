# Flights Globe (Next.js)

Web app that plots my flight history on an interactive globe, with a
Flighty-style passport derived from the same log.

## Data

`data/flights.csv` is the source of truth — one row per flight, columns
`date,src,dest,flightno`. Three reference tables resolve the codes:

- `data/airports.json` — `code -> { city, country, lat, lng, name }`
- `data/countries.json` — `code -> { continent, name }`, ISO 3166-1 alpha-2 keys,
  `continent` one of `af an as eu na oc sa`
- `data/airlines.json` — IATA carrier code -> `{ country, name }`

`scripts/build-data.mjs` validates the set and emits `data/flights.json`
(gitignored, regenerated by `predev`/`prebuild`) with each flight's `carrier`
parsed from its flight number. `lib/flight-data.js` imports that JSON, so
there's no database, no native module, and no filesystem access at request
time.

## Passport

`lib/passport.js` turns the log into the passport shown over the globe: country
stamps with first/last visit, continent coverage, trips, carrier shares, a month
heatmap, per-year rollups, records (longest/shortest flight, longest gap,
busiest month/route/airport) and the extreme points reached. `lib/geo.js` holds
the great-circle math and the block-time estimate (`km / 830 km/h + 0.5 h`).
Everything respects the HUD's year filter.

Trips are segmented by walking the legs in order and closing a trip when it
lands at a home base (or back where it started) and a real break follows, or
when the gap to the next leg is three weeks or more. Home bases are the airports
holding at least 10% of all *dwell days* — days between arriving somewhere and
departing it again — which is what separates BUF/PHX from a two-week holiday
airport. A filtered year reuses the home bases derived from the whole log, so a
single year cannot promote a holiday airport into a base.

## Globe layers

- **Visited countries** — shades the visited countries with Natural Earth
  outlines, matched by `ISO_A2`; the home country is gold.
- **Airport spikes** — each airport becomes a spike whose height and colour
  track how often it has been used.
- **Day / night** — `lib/solar.js` computes the subsolar point from NOAA's
  low-precision solar model (worst declination error 0.04° over 2026), and the
  globe gets a hemisphere cap centred on the antisolar point plus the terminator
  drawn as a great circle. No shader: the cap *is* the night side.
- **Colour by** — arcs coloured by year, airline (hues sampled around the wheel,
  since 15 carriers exhaust a categorical scheme) or arrival continent.
- **Fly on globe** — the passport's trips page isolates one trip's legs and
  frames them on their spherical centroid.

## Getting started

```bash
npm install
npm run dev
```

## Adding flights

Append a row to `data/flights.csv` — locally, or in the GitHub web editor from
any device. Pushing to `master` deploys.

```csv
date,src,dest,flightno
2026-09-14,buf,ord,ua3441
```

Dates should be ISO `YYYY-MM-DD`; `M/D/YY` is accepted and normalized. Airport
codes must exist in `data/airports.json` and their country in
`data/countries.json`, or the build fails with the offending line numbers — the
check that used to be a SQLite `FOREIGN KEY` constraint. An unrecognized flight
number prefix is a warning, not an error: the flight still plots, it just lands
in the `Unknown operator` carrier bucket until the code is added to
`data/airlines.json`.

`npm run data:fmt` rewrites all four files in canonical form: ISO dates,
lowercase codes, flights in chronological order, reference tables sorted by key.

## Deployment

Deployed on Vercel from `master`. The API routes are statically prerendered, so
the data is baked into the build and a log change ships on the next deploy.

## Scripts

- `npm run dev` / `npm run build` – `predev`/`prebuild` regenerate `data/flights.json` first.
- `npm run data:build` – validate the log and regenerate `data/flights.json`.
- `npm run data:fmt` – canonicalize `flights.csv` and the reference tables in place.
- `npm run lint` – Next.js lint.
